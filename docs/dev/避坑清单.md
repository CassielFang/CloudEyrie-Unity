# 避坑清单（Unity 版）

> **改代码前先读这份。** 每条都是这个项目**真实踩过**的坑，格式统一为
> 「现象 → 根因 → 怎么规避」。
>
> 来源：`docs/archive/计划-代码对照.md` §8（Cocos 时代的坑清单，约 30 条）+
> migration 后新增的 Unity 专属坑。**绑死 Cocos/Box2D 的条目已剔除**
> （`apply()` 重建夹具、`.webm` 不被 `cc.VideoClip` 识别、`LabelOutline` 废弃、
> `sp.Skeleton` 与 `cc.Sprite` 冲突、`Sprite.spriteFrame` 重置尺寸等）——
> 它们在 Unity 下不存在，需要原文可去归档里翻。

## 一、战斗与物理

### 判定盒的 `BoxCollider2D.offset` 必须为 0

- **现象**：朝左攻击打不到敌人；或者"攻击打到背后"。
- **根因**：左右镜像只翻**节点位置**，`offset` 不跟着翻。朝左时判定盒留在角色身后。
- **规避**：`offset` 恒为 0，位置全由节点承担。`onLoad` 会把 offset 折进节点位置并归零做兜底，
  但**别在 Inspector 里设 offset**。

### `AttackHitBox` 的刚体必须是 `Animated` 且 `allowSleep = false`

- **现象**：攻击"时灵时不灵"。
- **根因**：`Static` 的 fixture 不跟随节点变换；`Dynamic` 会休眠，而**休眠后接触事件不触发**。
- **规避**：照抄现有 `AttackHitBox` 的配置，别"简化"成 Static 或 Dynamic。

### 传感器之间不产生接触

- **现象**：把敌人碰撞体也做成 trigger 后，玩家再也打不到敌人。
- **根因**：`AttackHitBox` 本身就是 sensor，而 Box2D **不产生「触发器与触发器」之间的接触**。
- **规避**：要让玩家与小怪彼此不阻挡，走**碰撞矩阵**（`Core/PhysicsGroups.cs`），不要靠把敌人变 sensor。

### `Animated` 刚体忽略 `linearVelocity`

- **现象**：抛射物生成后钉在空中不动、也永远打不到人。
- **根因**：`Animated` 由节点变换驱动，写速度**完全无效**。
- **规避**：抛射物用 **Dynamic**（照抄 `MistShot` 的做法：`gravityScale = 0` + `bullet = true`）。

### 敌人碰撞体宽度必须小于两倍攻击距离

- **现象**："人物被小怪挤跑"。小怪一边"停在攻击距离"一边把玩家顶开。
- **根因**：小怪是"走到 `attackRange` 就停下开打"的。碰撞体一旦宽过 2× 攻击距离，
  它停下来时身体已经压在玩家身上。
- **规避**：碰撞体宽度 < 2 × `attackRange`（现用 64 宽 / 攻击距离 72，半宽 32 < 72）。

## 二、节点与引用

### 着地判定按 `WORLD` 层，不是按节点

- **现象**（历史）：角色站在灵泉石阶上时"不算着地"，水平速度不归零 → **一直滑**。
- **根因**：旧写法是 `collision.gameObject == groundNode` —— 只有场景里那一个 `Ground` 算地面，
  任何别的实心表面都不算。
- **现状**：已改为 `IsGroundContact()`：**层 == `PhysicsGroups.World` 且接触法线朝上**
  （法线朝上才排除"贴着屏障那面墙也算着地"，否则玩家能在半空凭空再跳）。
- **⚠️ 别再改回按节点判定。** 这条现在是"运行时新建的平台也能站上去"的基础。

### 节点引用必须在正确的时机取

- **现象**：小怪不转身；或 `groundNode` 指不到，`grounded` 永远 false、`jumpCount` 永不重置，
  表现是「跳两次之后再也跳不起来」。
- **根因**：`getChildByName('Art')` 这类查找是**一次性**的。
  先挂组件、再建子节点 → 拿到 null → 该功能整条失效。
- **规避**：**子节点必须在依赖它的组件之前建**；运行时的节点引用要在正确时机取，取不到时 `warn`。

### `GetComponent` 只找本节点

- **现象**：跨节点拿组件恒为 `null`，功能静默失效（例如背景自漂移从没被设过）。
- **根因**：`GetComponent` 只找**本节点**，不找别处的节点。
- **规避**：跨节点一律走显式引用（Inspector 拖拽或 `GameObject.Find`），
  **并且取不到时要 `warn`** —— 别再让它静默。

## 三、序列化与配置

### MonoBehaviour 的默认值会冻结进场景

- **现象**：改了 C# 里的默认值，运行时读到的还是旧值，**且不报错**。
- **根因**：组件加进场景的那一刻，Inspector 的值就写成**序列化数据**存进 `.unity` 了。
  之后改代码里的默认常量对已存场景**毫无影响**。
- **规避**：排查"改了代码没反应"时**先看 `.unity` 里存的是什么**。要改就改场景里的值。

### ScriptableObject 的默认值同理

- **现象**：改了 `GameConfig.cs` 里字段的默认值却没重建 `.asset`，运行时读到的还是旧值。
- **根因**：同上 —— 默认值只在**资源缺失**时生效，真值在 `Assets/Resources/GameConfig.asset` 里。
- **规避**：改数值改 Inspector（改 asset），或者删掉资源让它重建。

### 序列化结构变化，老数据补不上

- **现象**：给某个被序列化的类型**新加一个字段**，已存场景/资源里那份**没有这个键**，
  而 Unity **不会**用类默认值去补 —— 新字段在运行时恒为默认值/`null`。
  症状是"改了默认值但画面纹丝不动"，且**只有老数据复现、新建的正常**，极易误判成别的原因。
- **规避**：新增字段后**必须迁移老数据**，或在运行时按身份补齐缺失的键（参考 `ParallaxBackground` 的 `mergeDefaults` 写法）。

## 四、动画与美术

### 换美术素材要改「天然朝向」常量

- **现象**："攻击打到背后"。
- **根因**：翻转逻辑依赖一个「素材天然朝向」常量，判错整个左右反掉。
  更阴的是**同一角色的不同动作朝向可能相反**（美术交的"行走"朝右、"攻击"朝左），
  没有任何单一常量能同时满足。
- **规避**：接新素材时**先并排比一眼朝向**；多段素材朝向不一致时在美术流水线里镜像统一。
  相关常量：`QingheController.ArtNaturalFacing`、`CombatController` 的斜线朝向常量。

### 动画暂停要按「有没有真在动」，不是按状态

- **现象**：小怪原地踏步。
- **根因**：巡逻的到点停留、攻击冷却时都是「状态没变但人站着」。按状态切会让它一直播走路。
- **规避**：取**刚体速度**判定 —— 站住时 `pause()`、动起来 `resume()`。

### 青禾图集是预乘 alpha，而工程是 Linear 色彩空间 ✅ 已解决（2026-10-12）

- **现象**：控制台常驻一条 Spine 警告
  `Premultiply-alpha atlas textures not supported in Linear color space!`。
- **根因不是配置写错，是数学上矛盾**：Linear 空间下贴图要做 sRGB → Linear 转换，
  那是个**非线性**操作。预乘 alpha 要求「先线性化再乘 alpha」，但预乘好的数据里
  RGB 已经乘过 alpha 了 —— 再线性化等于把 alpha 也一起非线性化。
- **实测证据**（量 `青禾1.png`）：`alpha == 0` 的 818959 个像素 RGB **全为 0**；
  半透明区没有一个通道 `RGB > alpha`。这两条正是预乘 alpha 的特征。
  另外 `青禾1.atlas.txt` 里**没有 `pma:` 声明** —— 文件说直通、数据是预乘，本身就自相矛盾。
- **修法**：`python tools/unpremultiply_atlas.py` 把数据反预乘成直通 alpha，
  再把材质的 `_StraightAlphaInput` 设成 `1`。
  ⚠️ **缺一不可** —— 只改数据不改材质会把 alpha 乘两次（边缘发暗）；
  只改材质不改数据会把预乘当直通（边缘发亮）。
- **⚠️ 什么时候要重跑**：美术从 Spine 编辑器**重新导出图集**之后，预乘数据会回来，
  警告复发。和 `Assets/Spine/UNITY6.6-PATCH-NOTES.md` 是同一类「就地修改会被覆盖」的问题。
- **附带**：本工程两个 Spine 材质**都**要改（`Qinghe1_Mat.mat` 是场景在用的，
  `青禾1_Material.mat` 是另一套，容易漏）。
- **可能的后遗症**：反预乘后全透明像素仍是黑色，双线性过滤会在边缘采样到它们。
  若日后发现角色边缘有一圈暗边，补一步「alpha 扩张 / bleed」即可（脚本里已注明）。

### `SkeletonDataAsset.scale` 会把动画位移**一起缩放**

- **现象**：程序生成的骨骼动画「生效了，但幅度只有设定值的约 1/5」，
  而且**看截图几乎看不出来**（角色只是"动得有点小"，不像坏了）。
- **根因**：青禾的 `Qinghe1_SkeletonData.asset` 里 **scale = 0.2025**，
  spine-unity 加载时会把骨骼位置**连同动画里的位移偏移**一起乘上它。
  按 JSON 原始骨骼单位写 ±72 的步幅，实机只有 ±14.6。
- **怎么发现的**：量 `leg-l` / `k5` 的**世界坐标**，对比设定值与实际位移算出比例 ——
  **靠肉眼看截图是发现不了的**。
- **规避**：`tools/gen_spine_anims.py` 里所有参数统一用「缩放后单位」（≈ 世界单位），
  由 `to_raw()` 在写 JSON 前除以 `SKELETON_SCALE`。参照量：**腿长约 115、身高约 232**。
  改 `SkeletonDataAsset.scale` 的话这个常量要跟着改。

### 判断 2D 角色朝向：别量骨骼位置，要看贴图

- **踩到的**：量「后脑骨 `t` 在脖子 `bz` 右边」，据此推断角色朝左 —— 但代码常量
  `QingheController.ArtNaturalFacing = Right` 说的是朝右。**骨骼位置不代表美术朝向**
  （贴图挂点、绘制内容才是）。
- **规避**：放大渲染一张干净的 setup 位（清掉动画）直接看 ——
  青禾是**长发披在左侧、面朝右**。这也是团队自己定的规矩：
  「视觉相关的判断必须量数据或做并排对照图，不能靠肉眼扫一眼」，
  但**量错对象**同样会得出错误结论。

### 序列帧体积

- **现象**：把高分辨率序列帧全量塞进 `Assets/`，编辑器要为每个资源建导入项，
  选中大图还上传贴图，显存一紧就丢渲染上下文。
- **现状**：`Resources/video_fx/` 已占 **289 MB**（11 段 / 128 页），是仓库体量的最大单项。
- **规避**：新序列帧一律**按半分辨率打包**；播放走 `Fx/SequencePlayer` 的滑动窗口页缓存
  （只驻留播放头附近的页），不要一次性全加载。

### 回调不能设在内部 `stop()` 之前

- **现象**：「回调不生效」——例如小怪攻击播完不回走路（永久卡成一帧静止图）、
  Boss 转场永远不推进阶段。
- **根因**：`SequencePlayer.play()` 里先 `this.onComplete = cb`，随后 `start()` 内部调 `stop()`，
  而 `stop()` 里有一句 `this.onComplete = null`（给外部取消用的）—— **刚设的回调被自己清掉**。
- **规避**：凡是"回调不生效"，先查这里。设回调要在 `start()` 之后。

## 五、敌人与关卡

### 远程型的视野必须大于射程

- **现象**：「发现玩家后返回巡逻就不走路了」。
- **根因**：视野 == 射程意味着"看得见＝够得着"，它会一进视野就直接开打、永远不走过来。
- **规避**：视野取**射程的 1.5 倍**（现用 690 vs 460）。追击脱战线也要按**有效视野**算，
  不能用基础 `sightRange`。

### 远程敌人要离出生点比射程更远

- **现象**：「一启动立刻就冲我射一箭」。
- **根因**：射程 460、出生点 x=200，小怪摆在 640 → 距离 440 < 460，一进场就被发现。
- **规避**：按**最坏情况**算：`位置 − 巡逻范围 − 出生点 > 射程`。

### 关卡道具的 y 要按「内容底边」反推，不能拍脑袋

- **现象**：道具悬空或陷进地里。
- **根因**：美术原图是**打印级尺寸**且四周有大量透明留白（肉眼看不出来），
  图心 ≠ 内容中心。
- **规避**：按 `节点 y = GroundTopY + 内容底边距图心(px) × 缩放 − 压进地面多少` 反推。
  现有常量（`BarrierContentBottom` = 488、`SpringContentBottom` = 444）是按 `alpha > 8` 量出来的，
  **换素材必须重新量**。

### 平台必须先有美术

- **现象**：「莫名其妙看不到的障碍」——角色撞在空气上。
- **根因**：放过三个"只有碰撞体、没有贴图"的平台。
- **规避**：平台/机关**先有贴图再摆碰撞体**。这条现在也是关卡改造的前置条件。

## 六、资源加载

### `Resources.UnloadAsset` 会卸掉正在用的贴图

- **现象**：精灵变白块 / 闪烁。
- **根因**：`Resources.Load` 返回的是**缓存实例**，卸载会把正在用的贴图也卸掉。
- **规避**：不要在运行时对加载过的资源调 `UnloadAsset`；确需回收时走 `Resources.UnloadUnusedAssets`。

### `AudioSource.volume` 被夹在 `[0, 1]`

- **现象**：写大于 1 的增益被**静默夹成 1**，音效放大不生效。
- **规避**：音效放大只能**烘进 wav**（工具：`tools/normalize_sfx.py`）。
  另外峰值要留叠加余量 —— 顶到满刻度 + 多条一叠会硬削（听起来像"电流声"）。

## 七、灵炁系统

### 战斗来源是集合，销毁敌人时必须退订

- **现象**：灵炁恢复永久停在"战斗中"那档（1/秒），再也回不到 5/秒。
- **根因**：「战斗中」不是一个开关，而是 `setCombatSource(this, true/false)` 上报的**集合**
  —— 同屏多只敌人各报各的，任一只在场就算战斗中。销毁敌人时**必须退订**，否则那条记录永远留着。
- **规避**：敌人 `OnDestroy` 里必须 `setCombatSource(this, false)`。

### 灵泉的「在泉中」是静态位，跨场景会泄漏

- **现象**：灵雾形态**完全打不出灵弹**，且没有自愈路径；全图 30/s 回炁。
- **根因**：`SpiritEnergySystem.SetInSpring` 是 **static**（跨场景活着），而关卡实例的 `_inSpring` 每关重建为 false。
  玩家在泉里切场景 → 静态位停在 true → 新场景第一帧算出 `near = false`，与实例的 `false` 相同
  → **一句通知都不发** → 静态位永远是 true。
- **规避**：关卡重建时**先无条件清掉这一位**（见 `LevelDirector.BuildLevel` 开头）。

## 八、编辑器工具与工程设置

### `SerializedProperty.intValue` 写 `uniqueID` 会被静默归零

- **现象**：用脚本给 `TagManager.asset` 加排序层（Sorting Layer），层**名字写进去了**，
  但 `SortingLayer.NameToID("Background")` 返回 **0** —— 层还在，却塌回 `Default`，
  等于没加。文件里看 YAML 一切正常。
- **根因**：排序层的 `uniqueID` 是 **uint32**，而 `SerializedProperty.intValue` 是有符号的。
  Unity 给排序层算 id 用的是 **FNV-1a 32 位哈希**，约一半的名字结果大于 2³¹
  （按 int 看是负数）。写负数进去，Unity 当成非法值**归零**。
- **规避**：**必须用 `idProp.uintValue`**。本工程 11 个排序层里有 4 个（Background / Ground /
  Hazard / BarrierFront）会踩到这个 —— 见 `Assets/Editor/CloudEyrieProjectSetup.cs` 的 `WriteId`。
- **附带**：`Object.GetInstanceID()` 与带 `FindObjectsSortMode` 的 `FindObjectsByType`
  在 Unity 6.6 都是 **error / warning 级废弃**，要用 `GetEntityId()` 与不带 SortMode 的重载。

### 纹理导入器只认「根目录的 Resources」会漏掉嵌套的

- **现象**：美术放进 `Assets/Levels/<关>/Resources/…`，`Resources.Load<Sprite>` 返回 null，**不报错**。
- **根因**：导入器原来判的是 `path.StartsWith("Assets/Resources/")`。
  但 Unity 把**任何**名为 `Resources` 的文件夹都并入全局命名空间，嵌套 Resources 下的图
  **本来就必须** ppu=1；判成"非美术"就按 Unity 默认的 **ppu=100** 导入。
- **规避**：判据改成 `path.Contains("/Resources/")`（前后带斜杠，避开 `Assets/MyResources/`）。
  见 `Assets/Editor/CloudEyrieTextureImporter.cs`。

### MCP 插件会**自己改 `manifest.json` 的包版本**，升级失败会让整个 Unity 编译不了

- **现象**：控制台刷出几十条 `CS0234/CS0246`，全在
  `Library/PackageCache/com.ivanmurzak.unity.mcp.{animation,timeline}@…` 里，
  报「`com.IvanMurzak.Unity.MCP.Editor` / `AIGD` / `AssetObjectRef` 找不到」——
  也就是扩展包看不见核心包的程序集。**整个 Unity 进不了 Play，MCP 也一起断**。
- **根因**：`com.ivanmurzak.unity.mcp` 这套插件**会自行升级自己**。
  2026-10-12 它就静默把三个包一起改了版本
  （核心 `0.93.3 → 0.93.4`、animation `1.2.34 → 1.2.35`、timeline `1.0.19 → 1.0.20`）。
  新版扩展引用了新版核心才有的命名空间，而这次升级是「半截」的 → 编译崩。
- **它一定不是你改代码改出来的**：先跑
  `git log --oneline --name-only -- Packages/` 确认最近的 Packages 改动是谁的提交。
- **恢复（一行版）**：
  ```bash
  git checkout -- Packages/manifest.json Packages/packages-lock.json
  ```
  然后让 Unity 重新聚焦窗口 —— 它会**自动重新解析**到旧版本并清掉坏缓存
  （实测：`Library/PackageCache` 里那三个目录会换成旧版本的同名新目录，坏的那批被删掉）。
- **护栏**：`Packages/manifest.json` 与 `packages-lock.json` 都是被 git 跟踪的，
  所以插件一旦又自动改版号，`git status` 会立刻显示出来 —— **提交前扫一眼这两个文件**。

### 从非 Bootstrap 场景起播 → 重力差 32 倍，且不报任何错 ✅ 已修（2026-10-13）

- **现象**：打开 `Host` 或某个关卡场景直接按 Play，角色跳跃/弹跳**飞 32 倍高**，
  一弹就出屏幕。**没有任何报错**。
- **根因**：本工程重力必须是 Cocos 的 `(0, -320)`，而 Unity 默认是 `(0, -9.81)` ——
  `PhysicsUnits.Apply()` 负责改，但它**只由 `GameManager` 调用**，
  而 `GameManager` 住在 `Bootstrap` 场景。不过 Bootstrap 就没有这一步。
- **为什么现在才暴露**：关卡模组化之后，「打开 Host / 打开某个关卡场景直接 Play」
  成了最自然的做法 —— 这正是最容易踩的时候。
- **判据（可从日志反推，不必读代码）**：`v² = v₀² − 2gh`。
  实测初速 560 → 444 对应上升 5932 单位，反解出的 `g` 正是 9.81 而不是 320。
  另一个更快的判据：**日志里没有 `[PhysicsUnits] 重力设为` 这一行**就是没跑。
- **修法**：`PhysicsUnits` 加了
  `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]`，
  无条件应用重力与碰撞矩阵，不再依赖入口场景。两个 `Apply()` 都已幂等。
- **教训**：这类「全局一次性的初始化」挂在某个场景的组件上，就等于
  **把「从哪个场景开始」变成了隐含前置条件**。模组化之后每个场景都该能独立跑起来。

### 关卡/场景改动后先跑一次体检

- **现象**：物体留在 `Default` 层 → **对谁都碰不到**（门拦不住人、地形踩上去掉下去），**零报错**。
- **根因**：`PhysicsGroups.Apply()` 会把 5 个游戏层与「其它一切层」的碰撞全部断开，
  而它有 `_applied` 幂等门 —— **运行时永远不会再校正**。
- **规避**：改完关卡/场景跑菜单 **CloudEyrie/校验当前场景**。
  它检查：`Default` 层漏网的碰撞体（error）、关键组件重复（error，additive 加载后会变现实）、
  空 `sprite`（warning）。见 `Assets/Editor/CloudEyrieSceneAudit.cs`。

## 十、编辑器脚本里的两个"静默失效"（2026-10-17，铺五境时踩到）

这两个都**不报错**，只表现为「玩家穿过地面掉下去」或「画了的地形不存在」，
而且浪费的是一整轮播放测试的时间。用编辑器脚本批量建关卡时必踩。

### 同一次调用里「新建资产 → 立刻用它」会静默失效

- **现象**：脚本里先 `AssetDatabase.CreateAsset` 建了 Tile 资产，紧接着
  拿这个实例去 `tilemap.SetTile` —— **一格都没画上**，而 `SetTile` 不返回任何错误。
  火境因此地形全空，玩家出生后直接坠到 **y = -119862**。
- **判据**：`tilemap.GetUsedTilesCount() == 0`（这一句现在是我的第一道自检）。
- **规避**：**建资产与使用资产分成两次调用**；第二次从磁盘
  `AssetDatabase.LoadAssetAtPath<T>(...)` 重新读出来用。
  同样的坑在摆弹跳花时也踩过一次（当时是 Tile，这次还是 Tile）。
- **顺带纠正一个易误读的 API**：`Tilemap.GetUsedTilesCount()` 返回的是
  **不同瓦片的种类数**，不是格子数 —— 画了 100 格同一种瓦片，它返回 1。

### `CompositeCollider2D` 不会自动重烤

- **现象**：瓦片明明画上了（`localBounds` 也对），但
  `composite.pathCount == 0` —— 地形对谁都不存在，人直接穿下去。
- **规避**：改完瓦片后要**先关后开**再生成：

  ```csharp
  tcol.enabled = false; comp.enabled = false;
  Physics2D.SyncTransforms();
  comp.enabled = true; tcol.enabled = true;
  comp.GenerateGeometry();
  Physics2D.SyncTransforms();
  ```

  只调 `GenerateGeometry()` 是不够的 —— 它不会让 `TilemapCollider2D` 重新烘焙形状。
- **验收判据**：`composite.pathCount > 0` 且 `bounds.max.y` 等于预期地面顶边。

### 建完一段地形后，先量三个数再进播放模式

铺地形这一步的验收不该靠"进去走走看"，而是脚本跑完立刻打三行：

```
瓦片种类数   （0 就是没画上）
composite.pathCount   （0 就是没烤出来）
composite.bounds      （顶边该等于 GroundTopY）
```

这三个数任意一个不对，进去必然是"掉下去"，白跑一轮。

## 十一、按设计稿重排机关时踩到的（2026-10-17，第二轮）

这一节的共同点是：**生成出来的东西"看起来对"，但玩家踩在空气上 / 门挡在别处**，
而且全都不报错。

### 设计稿 SVG 里的同心图形是装饰，不是第二个物件

- **现象**：解析设计稿时，木境起点传送门多出一个「平台」、土境多出一个「落石预警」、
  金境多出一个「剑轮」；重排工具于是去找一个**不存在的对象**，或者把某个机关拉去错误的位置。
- **根因**：传送门画了两层椭圆（外框 + 内芯光晕）、剑轮画了外环 + 轴心圆，
  **圆心相同**。解析器按颜色分类，内芯的颜色恰好和另一种机关相同（木境是平台绿、
  土境是预警红），于是被当成独立物件。
- **规避**：`tools/gen_level_layout.py` 里维护 `seen_centers`，**同心的第二个椭圆/圆直接跳过**。
  改解析规则后务必重跑、并核对每境的数量。

### 不同语义的图形可能共用一种颜色

- **现象**：水境生成了一整条 1440×48 的隐形实心"平台"，横跨溪流；玩家能踩着水面走过去。
- **根因**：设计稿用同一种蓝色 `#4a8ab8` 画**水面**（溪流/水池），而 `#6ab8d8` 才是浮台。
  颜色 → kind 的映射把水面也当成了 `Platform`。
- **规避**：`CFG["Shui"]["#4a8ab8"] = "Water"`（不是 Platform）。**水面、水流、瀑布都要单独分类**；
  换境/改配色后先看一遍每张 SVG 的 `fill` 语义，别只看形状。

### 静态平台碰撞体不能覆盖"会动的平台"

- **现象**：移动平台从脚下走开了，玩家还站在原来的位置；藤蔓还没长出来，玩家已经能踩上去。
- **根因**：`LevelLayoutBuilder` 给设计稿里**每个** `Platform` 都生成了一个静态盒子，
  但其中一部分其实是移动平台（摆荡藤台 / 浮石 / 升降石柱 / 磁力平台）或藤蔓阶梯。
- **规避**：`LevelMechanismAligner` 把机关挪到位后，按「中心 x + 顶边 y」删掉
  `PlatformColliders` 里对应的静态盒子（`DropStaticPlatforms`）。
  **改完设计稿重跑顺序必须是：重建地面 → 重排机关**。

### 门的阻挡体被摆到了局部坐标 = 根的世界坐标

- **现象**：灵界屏障 / 剑气门 / 水幕**看起来在**，灵雾态切过去也"能穿"，
  但实体态同样能穿 —— 门根本没挡过路。
- **根因**：`ElementBarrier.blocker` / `GroupGate.blocker` 是**子节点**，局部坐标应为 0。
  土 / 金 / 水三境的局部坐标被写成了根的**世界坐标**（例如根 x=9100、阻挡体局部 x=9100），
  于是阻挡体跑到了 18200。
- **规避**：`LevelMechanismAligner.FixBlockers` 会把所有 barrier/gate 的 blocker 局部坐标归零。
  **新摆门时先看一眼 Blocker 的 localPosition 是不是 0**。

### 设计稿的「岩浆条」是示意，不是可碰撞区域

- **现象**：按设计稿坐标挪岩浆，会把它挪到实心地面段下面，同时让某些坑**失去安全网**
  —— 掉下去一直落，没有复活点。
- **根因**：设计稿用一条长条表示"这一段有岩浆"，横向跨度会跨过地面段；纵坐标也不是碰撞体的位置。
- **规避**：**面积型危险区（Lava / Pit / 坠落区）不跟着设计稿挪**，
  按场景里真实的坑位摆放。重排工具会明确打印「保持 Lava 系列」。

### 设计稿侧视图不画段 0 的教学敌人

- **现象**：按顺序硬套敌人位置，段 0 的热身战敌人被一路拉到段 3。
- **根因**：设计稿的敌人是用小圆点示意，段 0 的那只**根本没画**（正文里写了"一只山魈热身战"）。
  木境正文 5 只、图上 4 只；火/土/金/水也各少画一只。
- **规避**：重排工具把 `x < 900` 的对象排除在匹配之外（"段 0 教学敌人，保持原位"），
  其余用**最小总距离匹配**而不是按 x 排序硬套。
  数量对不上时先看设计稿正文，别只看图。

## 十二、镜头 / 背景 / 地面（2026-10-17，第三轮实测）

### 背景会「慢慢飘走」

- **现象**：开场站着不动，远景会一直往一个方向缓慢滑，几分钟后画面一侧露出空白；换关后还会带着上一关的偏移量继续滑。
- **根因**有三个，叠在一起：
  1. `autoPanSpeed` 是**单方向累加**（`_pan += speed × dt`），不是来回摆；开场 cue 在玩家走到 `atX` 之前一直生效。
  2. `MaxPan()` 的安全余量公式把 **`+ factor × travel`** 写成了正号 —— 把「需要的宽度」当成了「多余的宽度」，算出来的可推距离比真实余量还大。
  3. 换主题时没有重置 `_pan`。
- **规避**：`ParallaxBackground` 现在有 `autoPanLimit`（硬上限 120）、`MaxPan` 用 `actualW − LayerWidth` 算余量、`ApplyTheme` 里 `_pan = 0`。
  需要「来回缓慢移动」时用 `drift`（正弦、有界），不要用 `autoPanSpeed` 做长时间效果。

### 相机纵向跟随：死区不能用「目标空间」算

- **现象**：开了纵向跟随之后，玩家掉进坑里，相机停在半路，角色从画面下沿消失。
- **根因**：死区加在 `玩家y + verticalOffset` 上——偏移 275 已经把角色放在画面下半部，再加 200 的死区，角色实际可以离相机中心 475，而视口半高只有 360。
- **规避**：默认 `verticalDeadZone = 0`（直接跟随，角色在屏上的纵向位置恒定）。要开死区必须小于 `视口半高 − verticalOffset`（本作 = 85）。
  **（第四轮已重做：改成屏幕空间的不对称死区「上 80 / 下 300」，见第十三节；`verticalOffset` 已移除。）**
- **附**：`levelBottom/levelTop` 在 **LevelDefinition.asset** 里，不填就是 0 = 不跟随；改了代码默认值对已存在的 asset 无效。

### 地面：贴图、碰撞、旧的 Tilemap 三者会各说各话

- **现象**：有的地方能看到地但踩下去是空的；有的地方看不见地却站得住；相机往下一点就露出一大块深色棋盘格。
- **根因**：
  1. 上一轮把 `TilemapRenderer` 关了，以为「背景长卷自带地面」—— 但长卷是一张远景山水（底部是水/雾），不是玩法地面；
  2. 旧 Tilemap 的 **TilemapCollider2D / CompositeCollider2D 还开着**，按**上一版**的 4 块方块继续挡人；
  3. 场上只剩 `GroundArt`（1400 宽的石台占位图），其余地方没有地面贴图。
- **规避**：`LevelLayoutBuilder` 现在会
  - 把地面碰撞体**吸附到 64 格**（和 Tilemap 的格子一致），
  - 按同一组格子重画 Tilemap，开 `TilemapRenderer`，
  - **关掉 TilemapCollider2D**（碰撞只由 `GroundSegments` 的 BoxCollider2D 负责），
  - 关掉旧的 `GroundArt` 占位图。
- **验收**：进游戏后地面连续、坑的宽度和碰撞缺口一致；`Terrain` 的 TilemapRenderer=on、TilemapCollider2D=off。

### 存档点 id 必须是场景里**真实存在**的对象名

- **现象**：死亡重开提示 `找不到入口点`，玩家落回出生点（或原地）。
- **根因**：`Checkpoint.checkpointId` 写的是 `mu_spring`，而场景对象叫 `Spring_Checkpoint`；
  `LevelHost` 换关时用这个 id 当 `entryMarkerId` 去找 Transform，找不到只打一条 Warning。
- **规避**：checkpointId 改成对象名（现统一 `Spring_Checkpoint`）；`LevelHost` 换到**另一关**时清空 `CheckpointId`。

### 新加的序列化字段会冻在已有场景里

- **现象**：代码里把 `verticalDeadZone` 的默认值从 200 改成 0，进游戏读到的还是 200。
- **根因**：`CameraFollow` 在 `Host.unity` 里是已存在的组件；字段一旦被场景序列化，就按场景里的值走，
  改 C# 默认值不会回写。
- **规避**：加/改字段后，用 `SerializedObject` 显式写一遍并保存场景（`FixCamFields` 这类一次性脚本），
  再进 Play 验证。与 `[[monobehaviour-defaults-frozen-in-scene]]` 同源。

## 十三、弹跳花碰撞盒与相机手感（2026-10-17，第四轮）

### 弹跳花的碰撞盒比立绘高出一大截

- **现象**：角色在花朵**上方约 90 单位的空气里**被弹起；站在花旁边时触发区又已经包住了人。
- **根因**：碰撞盒是 110×160，而立绘 `mechanisms/bounce_flower`（318×149）按宽度 1.35 倍拟合后
  只有约 70 高，且**底边对齐碰撞盒底边** —— 盒子顶端比画出来的花高出约 90。
- **规避**：`LevelMechanismAligner.AlignBounceFlowers` 现在会把
  碰撞盒缩到 **宽 = 设计稿花盘宽度、高 = 宽 × 立绘纵横比**，立绘铺满盒子；
  `MechanismArtWirer` 的弹跳花拟合系数也从 1.35 改成 1.0（否则重跑补美术会把立绘再放大回去）。
- **验收**：`BoxCollider2D.bounds` 与 `Art` 的 `SpriteRenderer.bounds` 应完全相等（误差 < 0.2）。

### 平台跳跃相机：死区 → 阻尼 → 预看

- **现象**：角色一动镜头就跟着走，跳一下镜头上下抖；换成「完全跟随」后掉坑又会跟丢。
- **业界通行做法**（Cinemachine Position Composer 的三个参数就是这个）：
  1. **死区**：角色在窗口内走动时相机不动（横向约 0.1~0.2 屏宽）；
  2. **阻尼**：出窗口后用指数/弹簧平滑追，帧率无关；
  3. **预看**：朝移动方向多给一点视野，按速度缓入缓出，停下收回；
  4. 相机逻辑放 **LateUpdate**（物理步之后），否则会抖一帧。
- **本作参数**（`CameraFollow`）：横向死区 ±140、预看 150（速度归一化到 160）、
  纵向死区「上 80 / 下 300」、纵向平滑 10。
- **纵向为什么不对称**：相机跟的是**脚底**，人物往上还有约 230 的身高。上面留 80、下面留 300，
  普通跳跃（160）不会抖镜头，坠落时也不会出画。窗口参数必须按「脚底 + 身高」算，
  不能拍一个对称值。

## 十四、机关手感与引导（2026-10-17，第五轮实测）

### 移动平台的刚体必须是 Kinematic + 冻结旋转

- **现象**：火境的浮石平台一碰就**飞速自转**，玩家站上去整个平台翻起来。
- **根因**：`LavaStone_*` 在场景里存成了 **Dynamic**、没冻结旋转。
  `MovingPlatform` 每帧直接写 `transform.position`，但 Dynamic 刚体仍会接收接触冲量，
  玩家一站上去就给它加了角速度。
- **规避**：`MovingPlatform.Awake` 强制 `bodyType = Kinematic`、`freezeRotation = true`、
  `gravityScale = 0`。场景里也直接存成 Kinematic（不要再手摆成 Dynamic）。

### 小怪缩放：改 `artScale` + 同比例缩碰撞盒，底边不能动

- **现象**：按 0.6 缩了立绘，小怪却**浮在半空**。
- **根因**：`MinionVisual` 在 `Start` 里按 `artScale` 缩放立绘，运行时再按
  **碰撞体底边**对齐；如果只改立绘不改碰撞盒，缩放中心（立绘锚点）会把脚抬起来。
- **规避**：`artScale = 0.6` 的同时把碰撞盒 `size × 0.6`、`offset.y = 旧底边 + 新高/2`
  （底边保持不变 = -86）。`MinionVisual.AlignArtToGround` 会自己把立绘脚底对到新盒底。

### 无底坑不只吃玩家，也吃小怪

- **现象**：木境教学小怪会追进坑里，一路掉到 **y = -60 万**；它永远算「活着的敌人」，
  清场类条件（屏障 `requireEnemiesCleared`、`OnAllEnemiesCleared` 编排）永远不满足。
- **规避**：`EnemyAI.Update` 开头判 `y < -1000` 直接 `Destroy`。玩家侧的同款保险丝在
  `LevelRuntime.fallKillY`。

### 相机：坠落要看得到落点，落地要**缓**回正

- **需求**：下落时角色在画面中上部（提前看到落点）；落地后不"啪"一下回到常规构图。
- **做法**（`CameraFollow`）：
  - 着地：目标 = 脚底在中心下方 `restScreenY(275)`，回正速度 `landingRecoverSmooth(2.5)`；
  - 下落速度 > `fallLeadSpeed(120)` 且未着地：目标 = 脚底在中心上方 `fallScreenY(90)`，
    跟随速度 `verticalSmooth(10)`（跟得慢就会掉出下沿）；
  - 其余空中：不动，只在头顶快出画（上 80）/脚底超下沿（下 300）时夹紧。
- **换关/坠落重开的坑**：`LevelHost.PlacePlayerAndCamera` 必须调 `SnapVerticalToRest()`。
  不调的话相机会保留上一步的 `_cameraY`（比如坑底 -540），而开场 cue 又会把相机锁住，
  表现是"复活后角色一直贴在画面上方，走一段才回落"。

### 引导：示能 → 被挡住时的分级提示 → 反馈

参考了平台跳跃解谜的通用做法（**示能一致 / 分级提示 / 不让玩家觉得自己被当傻子**）：

1. **示能（不弹字）**：火盆美术只交付了「已点燃」一张图，原本未点燃也像烧着。
   现在未点燃时**压暗染色**，玩家靠近时轻微脉冲、并往暖白提一点色 —— 一眼能看出"这个能互动"。
2. **分级提示**：`GroupGate.lockedHints` 三条，以「玩家站在门前且门还关着」为触发条件
   （不是全局定时器），1.2s 后第一条、之后每 6s 下一条：
   现象 → 动作 → 规则。提示时把同组未点亮的火盆脉冲高亮一次，让视线落到正确的东西上。
3. **进度反馈**：点亮一座、同组没全亮时，火盆直接提示「还有一座火盆未点燃」，
   避免玩家以为已经完成、站在门前反复撞。
4. 剑碑门（金境）用同一套字段，提示改为「灵合态按 壹→贰→叁 共鸣」。

**原则**：提示只在"卡住"时出现（门前停留），不会在玩家还没到时剧透；
每个谜题记住自己提示到第几级，不重复最模糊的那一条。

### 机关立绘尺寸要按"玩家身高"校一遍

- **现象**：屏障/门像一座庙（722 高，玩家约 230）、火盆和玩家一样高、火墙是一扇**石质水门**。
- **根因**：屏障用固定 `BarrierArtScale=0.68`（与碰撞盒无关）；火盆按碰撞盒高度的 1.5 倍拟合；
  火墙直接套了通用屏障图。设计稿里这些东西只有 110~320 高。
- **规避**：屏障 0.42、火盆 1.0；火墙单独用**火柱立绘排一排**（`MechanismArtWirer.WireFireWall`）。
  新接机关时先问一句"它和玩家谁高"。

### 教学小怪不能摆在悬崖边

- **现象**：五境段 0 的小怪都在 x=700，而第一段地面到 x≈704；巡逻范围 ±140，
  一转身就走出地面边缘、掉进坑（旧代码还会一直掉到 y=-60 万）。
- **规避**：教学小怪统一 x=450；`EnemyAI` 增加 y < -1000 自动销毁兜底。

### 相机下潜要先把"地下"画出来

- **现象**：相机跟着角色掉坑后，坑底露出的是**背景长卷**（天空/水面），像"世界穿帮"。
- **规避**：每境在地面顶线以下铺 `GroundBackdrop` 深色土幕（Default -150，背景之后、地面贴图之前）。
  有新的坑或改了地面高度，记得同步土幕的范围。

## 十五、跳跃手感 / 骨骼动画 / 特效 / 相机下潜（2026-10-17，第六轮）

### Spine IK 目标超出骨链长度 = 四肢「折断 / 锁直」

- **现象**：程序生成的走路/跳跃动画里，腿或手走到某个位置会突然变成一根直棍，像折断。
- **根因**：生成器驱动的是 IK **目标骨骼**；目标到骨链根的距离超过链长时，IK 无法解算，
  链会沿目标方向锁成直线。实测 setup 状态下：
  - 右腿链 461.3，目标距 **470.6（102%）** —— 一开始就够不着；
  - 右臂链 292.1，目标距 **296.6（101.5%）**；
  - 左腿 98.9%，摆幅一加就超。
- **规避**（`tools/gen_spine_anims.py`）：
  1. 每个肢体加**基础抬升**（把目标拉近，留弯曲余量）；
  2. 左右腿/臂的摆幅**分别给**（两条腿的链长本来就不同）；
  3. 生成后逐帧验算「目标距/链长」，≥99.5% 直接打印警告 ——
     **截图里几乎看不出来，只有这个数字能提前发现**。
  当前所有动作的最大利用率 ≤96.4%。

### 跳跃手感：土狼时间 + 输入缓冲 + 可变高度 + 非对称重力

- 之前只有「按下 → 立刻改速度」：走出平台边缘一帧就跳不了、落地前按的跳会被吞、
  一按就固定高度。现在（`EntityForm` + `QingheController`）：
  - `coyoteTime 0.10s`：离地后一小段时间还能跳；
  - `jumpBufferTime 0.12s`：落地前按下，落地当帧起跳；
  - 上升中松开跳键 → 竖直速度 ×`jumpCutMultiplier(0.45)`（可变高度）；
  - 上升 `riseGravityScale 0.9` / 下落 `fallGravityScale 1.35`，且**只对玩家自己起跳生效**，
    不改弹跳花的弹射手感。
- **二段跳改成「云跃」**：竖直速度固定（0.82×），按住方向键额外给
  `secondJumpHorizontalBoost(1.25)` 的水平加速 —— 它是有方向的空中位移，不是弱化版一段跳。

### 骨骼动画要接到玩法上

- **现象**：`tools/gen_spine_anims.py` 早就生成了 `run/jump/fall`，但 `SpineCharacterView`
  只播 `idle_breath`，游戏里永远看不到。
- **规避**：`SpineCharacterView` 按「形态 + 着地 + 速度」切换：
  实体形态下地面移动播 `run`、上升播 `jump`、下落播 `fall`；灵雾/灵合固定回 `idle_breath`
  （它们是飞行/悬浮，播跑步会很违和）。同名动画不重播（每帧 SetAnimation 会卡在第一帧）。

### 特效：交付层上千张图，别只留 5 张

- `美术素材/特效贴图/` 有 14 类、约 4700 张，但 `Resources/fx_tex/` 之前只有 5 张机关贴图。
- 新增入库（`tools/import_fx_tex.py`）：`fx_dust` / `fx_cloud_ring` / `fx_ring_white` /
  `fx_wave` / `fx_sparkle` / `fx_magic_circle` / `fx_slash_ink`。
- `InkFx` 新增 `JumpDust` / `LandDust` / `DoubleJump` / `Sparkle` / `MergeCircle`，
  由 `QingheController` 在起跳、二段跳、落地时自动触发；切灵合时额外放一圈法阵。
- **挑图判据**：alpha 要有真透明（接触表里的黑底是缩略图背景）；全不透的是材质不是精灵。

### 相机不要下潜到地下

- **现象**：开了坠落预看之后，相机跟着掉进坑里，画面露出地面截面的砖墙和背景长卷。
- **需求**：视野照到地面就够了，**不再往下钻**。
- **规避**：`CameraFollow.verticalFloor = 0`（Host 里显式写入）。所有纵向目标最后
  `Mathf.Max(wantY, verticalFloor)` —— 掉坑时画面停在地面构图，角色离开画面下沿后由
  `LevelRuntime.fallKillY` 重开。配合 `GroundBackdrop` 渐变土幕，坑口过渡也不生硬。

## 十六、长袍角色的跑跳动画 / 交付层特效替换（2026-10-17，第八轮）

### Spine 动画的 `angle` 不能乘 SkeletonData 的 scale

- **现象**：给头发/衣摆加旋转关键帧后，角度被放大 5 倍（1/0.2025），直接拧成麻花。
- **根因**：`SkeletonDataAsset.scale = 0.2025` 只缩放**位移**（translate），
  **角度是度、不随 scale 变**；`gen_spine_anims.py` 的 `to_raw()` 把 `angle` 也除了 scale。
- **规避**：`to_raw` 只缩放 `x/y`，`angle` 原样写。之前生成的动画只有 translate，所以这个 bug 一直潜伏着。

### 长袍角色：腿被衣服挡住，动画要从「上半身 + 衣摆」做文章

- **现象**：`run` 循环里腿在动，但长袍把腿全遮住，画面看起来像站着滑行；持剑手还会横举。
- **根因**：只驱动了腿/手 IK 目标；上半身只有很小的 bob；手目标没有跟着躯干前倾/起伏，
  躯干一动，手到肩的距离变化，IK 把持剑手越推越远。
- **规避**（当前做法）：
  - 躯干加 `lean_x` 前倾 + 保持 bob；
  - **手目标跟着躯干一起**平移（`lean_x`/`bob` 同量加到手臂 target）；
  - 持剑右手的摆幅 3°、并往身体内侧收；左手摆幅 14°；
  - 给 `t*` / `yb*`（头发、衣摆）骨骼加 3~5° 的二次摆动（`add_secondary_sway`）；
  - 起跳/下落把手臂目标抬得更高（48/40），长袖才看得出动作。
- **验收**：`validate()` 的 IK 余量全 ≤99.5%；跑/跳/落的单帧姿态用 `screenshot-isolated` 逐帧看过。

### 交付层特效：先看 alpha，黑底图必须抠

- **现象**：替换 `_bleed` 后，角色身上出现**一块黑方板**。
- **根因**：`yan1.png`（扭曲烟雾类）是**黑底 alpha 全 255** 的图；`copy` 进引擎后就是黑方块。
  同类问题此前在 `fx_flame` 上踩过。
- **规避**：`import_fx_tex.py` 里 `fx_smoke` 用 `key_black`；新挑的图先看
  `alpha == 255` 的占比，黑底一律抠。当前入库图里只有 yan1 需要抠。

### InkFx 已改为优先用交付层贴图

| 程序生成 | 交付层替换（`Resources/fx_tex/`） |
|---|---|
| `_bleed` | `fx_smoke`（yan1，抠黑底） |
| `_streaks[0..2]` | `fx_streak1/2/3`（trail0066 / trail014 / sn_zxb_texiao_028_lan） |
| `_glow` | `fx_glow`（08ce35de 柔光） |
| `_mote` / `_speck` | `fx_sparkle`（k_guangmang2 星芒） |
| `_ring` | `fx_ring_white`（e68de1d0） |
| `_arc` | `fx_slash_ink`（4604933d 白色回旋） |

前/后半环（`glow_ring_far/near`）交付库没有对应素材，仍保留程序生成；
`fx/*` 程序图保留为 `Resources.Load` 失败时的兜底。

## 十七、左右不对称的骨骼 / 手肘 / 头发（2026-10-17，第九轮）

### 左右腿链长不一样：短的会显得"一长一短"

- **现象**：侧身站立时右腿明显比左腿短，跑动时两条腿怎么调都不对称。
- **根因**：骨架本身就不是对称的 —— 左腿链 555.8 原始单位，右腿链只有 461.3；
  右腿 IK 目标还比左腿高 62 单位。
- **规避**（本轮做法）：**直接把右腿拉长**，而不是在动画里迁就它：
  - 给 `k6` 骨骼加 `scaleX/scaleY = 1.205`（461.3 × 1.205 ≈ 555.8）；
  - 右腿 IK 目标 `leg-r1.y` 从 38.18 改到 -23.97（和左腿同高）；
  - 之后左右腿的动画参数完全一致。
- ⚠️ 这是**骨架层**的修改，写在 `青禾1.json` 的 `bones` 里；美术从 Spine 重新导出会覆盖它，
  和生成动画一样要按交接文档重做。
- `gen_spine_anims.py` 的 IK 验算已改为：`链长 = 两段骨骼的实际世界距离 + 末段长度 × 世界缩放`，
  **不能把 data.length 相加** —— 骨骼 scale 不会写回 length。

### 手肘看起来"折断"：目标把手臂折得太紧

- **现象**：向右走时（屏幕右侧那只手）肘部折成锐角，长袖在肘部堆出一块三角。
- **根因**：IK 目标离肩太近，肘部被迫弯到 90° 以下；而长袖的蒙皮在锐角处会塌陷。
- **规避**：空闲手的目标**往下放**（`arm_l.base = -2`，不是 +4），摆幅从 14 收到 10，
  IK 利用率到 94.6%，手臂更舒展；持剑手只轻微内收（`base_x=-2`），不再横举。

### 头发/衣摆要"常驻"摆动，不能只写在跑跳动画里

- **现象**：站立时头发是一根硬棍；生成动画的摆动只在 run/jump/fall 生效。
- **规避**：新增 `Fx/ClothSway` 组件（挂在 `Art` 节点），在 LateUpdate 里给
  `t*` / `yb*`（发丝/衣摆）骨骼**叠加**一个 2.2° 的正弦旋转，再 `UpdateWorldTransform`；
  越靠末梢幅度越大。每帧都加在动画给出的角度上，不累积。
- 同时把生成动画里的二次摆动幅度加大（跑 6°、跳/落 8°），并按链深放大。
